# Architecture Note

## 1. Purpose and boundary of this note

This note is the architectural detail behind the shared-concern list in [`../README.md`](../README.md). It answers the questions the code cannot answer about itself: why there is exactly one implementation of each shared concern, when a Base UI import is allowed, what a later integration owner would replace and where, and where every reported number came from.

It holds five records:

- the layering rules and the import direction that enforces them (sections 2 and 3);
- the design-system boundary between substrate and fallback, and the register of what the design system does not supply (sections 4 and 5);
- the invariants lint enforces and those that stand as review discipline (section 6);
- the future-connection seam map, one entry per later owner (section 7);
- the media fixtures' provenance and licence, and the measurement method with its results (sections 8 and 9).

Everything else about the build lives in [`../README.md`](../README.md): commands and pinned versions, the dependency-to-job table, the seeded personas and session states, the development runtime, the simulated-effect labels, the divergences record, the known limitations and the named assumptions. Those two files are the only documentation deliverables.

The application is one Next.js 16 App Router package in a Bun workspace, with one typed in-process data service over a file-backed synthetic store. No external service is integrated in this build. Every external effect is simulated and labelled at the point the user triggers it.

## 2. Layering and import direction

One direction, enforced by lint rather than agreed by convention:

```
src/app  →  src/features  →  src/components  →  src/modules/data-service  →  src/modules/store
```

The framework-free domain modules — `money`, `time`, `support`, `content`, `audience`, `coaching`, `media`, `export`, `import` — sit beside that chain rather than inside it, importable from either side of the service. A domain rule therefore has one home, and a component that needs it imports it instead of restating it.

The direction exists for four reasons, each of which is a property of the delivered tree:

- **A Server Component reads through the service directly.** It calls `reads.*` from `src/modules/data-service`, and nothing on the server fetches `/api/*`: no `fetch("/api…")` call exists anywhere under `src/`. A prerendered fetch would fail the build, an on-demand one would pay a round trip for data the render already holds, and both would be a second path to the same authorisation.
- **A Route Handler is a thin adapter.** It reads the request, validates the body against its own Zod schema, dispatches to exactly one named mutation, and maps the result through `src/modules/data-service/response.ts`. A path may carry several mutations; each has its own schema, and no handler accepts a universal command.
- **Only two places reach the store.** `src/modules/data-service` (every read and mutation) and `src/modules/dev-runtime` (which seeds, generates and resets it). The `.oxlintrc.json` override forbids `@/modules/store/…`, a relative path into it and the sibling form `../store/…` from `src/app`, `src/lib` and `src/proxy.ts`, so neither a page nor the request-level file can open a data file even by accident. The proxy reads and mints the session cookie through `src/lib/session-cookie.ts`, where the cookie's name and the session-id grammar live, so the store is not reached for them.
- **A feature never imports a feature.** That is what puts the prose editor, the review panel and the record detail body in `src/components`: two families need each of them, and a feature-to-feature import would be the second copy the rule exists to prevent. `src/components/ui` imports neither a feature nor a domain module.

### The service is the only door

Every read returns an envelope, never a bare result, so a view can state what it is authorised to do and how much of the past its data covers.

| Field         | What it carries                                                                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data`        | the records the view needs, already scoped and projected; a field the caller may not see is removed before the envelope exists, not hidden in a component |
| `scope`       | the organization, ministry, support subject and principal the read ran under                                                                              |
| `source`      | `{ system, reference }`, the reference opaque: never parsed, never compared across systems, never rendered as if its form carried meaning                 |
| `revision`    | the revision a mutation originating from this view must present as `expectedRevision`                                                                     |
| `asOf`        | the scenario instant the read was evaluated at; two surfaces compare only when their `asOf` and coverage agree                                            |
| `coverage`    | `{ from, to, state }` with state `complete`, `partial` or `unknown`, plus currency and date basis on a financial read                                     |
| `valueStates` | field path → `value`, `zero`, `unknown`, `withheld`, `unavailable` or `incomplete-subtotal`, so no surface has to infer that a number is not a number     |
| `actions`     | the named actions currently available, with the reason when one is absent; advisory only, because the service re-checks on submit                         |

`incomplete-subtotal` is the one state an envelope derives rather than receives: `buildEnvelope` in `src/modules/data-service/envelope.ts` sets it for a recorded `value` or `zero` whose coverage is partial, and preserves `withheld`, `unknown` and `unavailable` as they are. A caller cannot choose it, so a component cannot invent a seventh state and cannot decide for itself whether a subtotal is incomplete.

Every mutation takes exactly four things, and nothing else: `{ operationId, scope, expectedRevision, payload }`. `operationId` is the caller's identity for the attempt. `scope` is the context the caller believes it is acting in, re-verified and re-checked against the scope the write produces. `expectedRevision` is what the caller saw. `payload` is validated before any state changes.

Every mutation answers with exactly one of eight outcomes. No mutation returns a bare boolean, and no caller infers success from the absence of an error.

| Outcome           | Trigger                                                               | What the caller receives                                                                   |
| ----------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `accepted`        | applied once                                                          | the new revision, the created or changed identifiers, per-item results                     |
| `alreadyAccepted` | the same `operationId` and `intentHash` replayed                      | the stored result, with no new effect and no new revision                                  |
| `unchanged`       | the payload would change nothing                                      | the current revision, with no history or activity entry                                    |
| `conflict`        | `expectedRevision` is stale, or the id was reused with changed intent | the current value beside the caller's preserved input                                      |
| `denied`          | a scope or permission check failed                                    | a reason code that reveals nothing about a hidden record's existence, count, title or size |
| `invalid`         | schema validation failed                                              | per-field messages keyed by field path                                                     |
| `unavailable`     | the source behind the read is down                                    | the source identity and guidance; never an empty list and never a zero                     |
| `unknown`         | the effect may have been applied but the acknowledgement was lost     | the `operationId` to re-query                                                              |

The operation ledger in `src/modules/data-service/operations.ts` is what makes a lost acknowledgement recoverable without a resend. Each attempt is recorded under its `operationId` with an `intentHash` of the scope and payload: `begin()` answers fresh, replay or changed-intent, `record()` appends, `lookup()` reads back. The same id with the same intent returns the stored result through `alreadyAccepted`; the same id with a different payload is a `conflict`, never a second effect.

Authorisation runs before anything is enumerated. `src/modules/data-service/authorize.ts` resolves the development session to a principal and admitted memberships and then answers `canView`, `canEdit`, `canExport` and `canReadProtected`, with `assertScope` and `assertScopeUnchanged` around every write. Because the check precedes enumeration, a denied read carries no count, title, existence flag or size, so a list, a search or a saved view cannot be used as a disclosure oracle, and a change cannot move a record into a context the caller cannot see.

### The transport: one per direction, and the status ladder

The browser writes through Route Handlers and the server renders through the service. There is no Server Action, no second transport and no server request to the application's own endpoint.

`src/modules/data-service/response.ts` is the one mapper from an outcome or a read result to an HTTP response, so every handler answers under one ladder and none picks a status of its own. The body always carries the outcome, or the envelope, itself: the status only names which answer that body is.

| Answer                                                      | Status |
| ----------------------------------------------------------- | ------ |
| `accepted`, `alreadyAccepted`, `unchanged`, a read envelope | 200    |
| `unknown`                                                   | 202    |
| `conflict`                                                  | 409    |
| `denied` when authority was refused                         | 403    |
| `denied` with `session-expired` or `session-unavailable`    | 401    |
| `invalid`, or a read's refused request                      | 422    |
| `unavailable`                                               | 503    |

Three of those rows carry a decision worth stating. `unknown` answers 202 because the request was well formed and the attempt is recorded under the caller's own id — the exchange succeeded while the effect's fate did not — so its body's `outcome: "unknown"` is the authoritative statement and every client here reads the body before deciding. A session fault answers 401 rather than 403, because the caller never reached the permission check and a permission refusal would be a false account. A read whose own query or segment is not one it admits answers 422 with the same field-keyed `invalid` body a malformed mutation earns, so a client reports a refused request rather than a source outage or a denial.

One transport decision is recorded because it refuses two parameters a reader might expect. `GET /api/variants` states `view` and `variantId` and refuses `audience` and `locale` by name instead of accepting either: an edition's audience and locale are properties of the variant that `variantId` identifies, and the read already states both in its envelope. There is no filter for those parameters to reach, the route does not invent a second read to give them one, and answering `invalid` tells a caller that no filter was applied rather than leaving it to believe it chose another edition. `POST /api/variants` creates one Update edition through `createVariant`, with the family pinned to `update`, so a request cannot create a Page edition through that path or carry a draft, a candidate or a notification intent through it.

`runReport` is the deepest of these, because it is what makes five surfaces agree. It takes one query — scope, period, currency selection, partner selection, sort, page — and returns one `ReportResult` carrying the summary, the series, the rows, the whole-result total, the coverage and the as-of instant. Four fixed reports are addressable through it (`received-period-and-year-to-date`, `monthly-history`, `partner-month-matrix`, `period-comparison`), and the same call serves the overview, the ledger, the matrix, the comparison, the chart, the drilldown, the CSV export and the print model. The service owns filtering, sorting, paging and aggregation; a page requests 50 rows by default and is clamped to 200, while `total` and every minor-unit sum remain whole-result values.

The 27 shared component files the plan enumerates — exclusive of `src/components/ui` and of its `direction` provider — are, in the order the plan groups them: shell (`app-shell`, `sidebar-nav`, `context-indicator`, `dev-banner`, `dev-panel`, `persona-switcher`); list and paging (`query-toolbar`, `record-list`, `pagination-bar`, `scroll-region`); detail (`record-detail`, `side-panel`); feedback and form (`form-field`, `action-review`, `operation-result`, `state-notice`, `status-badge`, `draft-status`, `simulation-label`); content and media (`chart-figure`, `review-panel`, `media-picker`, `video-player`, `variant-switcher`, `locale-switcher`, `context-switch-guard`); and the prose editor (`prose-editor`). One further file, `rendered-content.tsx`, is the application's single rendering boundary — the one place the HTML that `src/modules/content/render.ts` produces becomes DOM — and it is not one of the 27. Which routes and browser specs are composed against these surfaces is recorded in the README's verification record and known limitations; this section records ownership, which the tree satisfies.

**No second state owner.** TanStack Query caches read envelopes only, keyed `['scope', orgId, ministryId, supportSubjectId, '<job>', params]`, and the cache is cleared on a context switch so a stale result from the previous context cannot be rendered. Component state holds transient selection and editor text, never a record: the store is the only owner of a record, and a component that needs one reads it through the service.

**No wrapper that only re-exports.** `src/components/ui` composes primitives; it does not forward another library's API under a new name. A module exists when it owns a decision — a schema, a rule, an authorisation, a rendering — and the import graph reflects that: the domain modules are importable from either side of the service because a rule is sometimes needed to render as well as to read (`content` carries the document schema and its presentation choices, `media` the preparation states and refusal reasons, `money` the amount formatting, `support` the bucket names), and the code that needs one imports the module rather than a copy of its logic.

**One time model, evaluated at read time.** Every boundary is a pure function of `(input, now)` from `src/modules/time`, evaluated when a read or a command runs; nothing is enforced by a background job, so there is no scheduler to drift. The two window kinds are deliberately different and must not be described as one: a referral's New window is **calendar-day** arithmetic (D is day one, the last nominal included date is D+N−1, and the exclusive endpoint is the first valid instant starting D+N in the accepted source zone, where a missing midnight resolves to the first valid instant after the gap, a repeated midnight to the earlier offset, and a skipped date to the next existing date), while a continuation is **elapsed-second** arithmetic from the acceptance instant A (A + N × 86,400 s). The notification deadline is strict at equality at the intended instant + 24 elapsed hours, and the confirmation deadline is strict at equality at acceptance + 168 elapsed hours, so a request at exactly either boundary is refused rather than admitted.

## 4. The design-system boundary: substrate versus fallback

The boundary between "the design system uses Base UI" and "the application fell back to Base UI" is a location test, not a judgement call, because a judgement is what a reviewer and an author would settle differently twice.

- **Inside `src/components/ui`, `@base-ui/react` 1.9.0 is the primitive substrate of the generated Maia source** — the registry's own `button` imports `@base-ui/react/button`. That use is design-system source: it is neither a fallback nor a gap, and it needs no register entry. Twenty-four of the thirty-six component files import it, which is ordinary substrate traffic inside the folder the CLI owns.
- **Any `@base-ui/react` import outside `src/components/ui` is a fallback**, whether it sits in a feature or in a shared pattern, and it requires a gap-register entry in section 5 naming four things: the interaction, the UI SDK package and version consulted, the specific behaviour or WCAG criterion that fails without the substitution, and the component substituted. A fallback without that entry is a defect.
- **`@ui-sdk/*` is the first choice, reached only through one adapter.** `src/lib/ui-sdk.ts` is the only file in the tree that imports `@ui-sdk/core` or `@ui-sdk/react`, and it exposes four own-named behaviours — `useDismissableLayer`, `useRovingFocus`, `useTypeahead`, `useModalFocusContainment` — so a component calls the adapter and never the SDK. Its three consumers are `src/components/query-toolbar.tsx` (roving focus and typeahead over the facet list), `src/features/initiatives/components/member-picker.tsx` (the same two plus a dismissable layer) and `src/components/side-panel.tsx` (a dismissable layer for the desktop column and modal focus containment for the phone sheet).

**Today no `@base-ui/react` import exists outside `src/components/ui`.** The fallback path is available and unexercised: every generic behaviour this build needs is either substrate inside the design-system folder or supplied by the SDK through the adapter, so the register's single entry records a capability the SDK offers only through a whole primitive rather than a Base UI substitution.

**The pinned shape.** The shadcn CLI is 4.23.0; `apps/dashboard/components.json` records `style: "base-maia"`, `tailwind.baseColor: "zinc"`, `tailwind.css: "src/styles/globals.css"`, `cssVariables: true`, `iconLibrary: "lucide"` and aliases under `@/` with `utils` at `@/lib/cn`. `base-maia` is chosen over `radix-maia` deliberately: its component source imports Base UI, so the build carries exactly two primitive systems — UI SDK behaviours first, Base UI as substrate and documented fallback — and introduces no Radix.

The registry publishes 65 entries. The tree accounts for every one: **36 installed + 27 excluded + 2 deliberately neither = 65**, and `src/components/ui` carries the 36 component files plus the `use-mobile.ts` hook that ships with the sidebar source.

### Gap: modal focus containment

- **Interaction.** The record side panel's phone presentation is a bottom sheet whose initial focus must land inside it, whose Tab and Shift+Tab must wrap within it, whose Escape and outside presses must request a close, and whose focus must return to the control that opened it.
- **Package and version consulted.** `@ui-sdk/core` 0.1.0-beta.13 and `@ui-sdk/react` 0.1.0-beta.13.
- **What fails without a substitution.** The SDK's dialog preset contains focus and makes the rest of the page inert, but it is reachable only through a whole popup primitive (`definePrimitive`, `createPopup` and rendered parts), which a behaviour-only adapter cannot host without becoming a component. `bindLayer` alone dismisses on Escape and blocks presses outside it, yet leaves the Tab cycle free, and the helpers it uses internally are not exported from any public entry. A sheet built on `bindLayer` alone lets Tab walk out of the dialog, which breaks focus order for keyboard users (WCAG 2.2 SC 2.4.3) and makes the dialog's own controls hard to reach on a repeat visit.
- **Substitution.** `useModalFocusContainment` in `src/lib/ui-sdk.ts` supplies exactly that missing step and nothing else: focus lands on the caller's `initialFocusRef` or the first tab stop inside the dialog, a document-level Tab handler wraps forward and backward within it, `bindLayer({ modal: true })` keeps outside presses off the page and reports Escape, and `keepFocus` restores the invoking control. The handler and the layer are released in one cleanup, so the page is fully reachable the moment the sheet closes (SC 2.1.2). The dialog's `role`, accessible name and `aria-modal` stay with its own markup, and the component sets the substrate's `initialFocus={false}` so one owner places focus and the surface never carries two sets of focus guards.

**Inspected export list, and what the SDK supplies.** `@ui-sdk/core` 0.1.0-beta.13 publishes its root entry, per-component entries, `renderer` and `testing`; its `foundation/*` modules are internal and unreachable. The root exports `bindLayer` with `LayerDismissReason`, `keepFocus`, `createFocusRecovery`, `createRovingFocus` with its item and options types, `createClaim`, `createTypeahead`, `isTypeaheadKey`, `isComposing`, `labelOf`, `createListbox`, `createPopup` with the popup presets on their component entries, `bindPersistentLayer` and the `Store` type. `@ui-sdk/react` exports the hooks `usePrimitive`, `usePart`, `useNearest`, `useHandle`, `useAround`, `usePreference`, `useShortcut`, `useShortcutHint`, `useAsyncOptions`, `useFieldControl`, `useJoinField`, `usePlacedContent`, `useSegment` and `useToolbarScope` — none of them one of the four behaviours — and its `./primitive` subpath exports `mergeProps` and `renderElement`. The adapter builds the item props it returns on `mergeProps` rather than hand-writing them, because joining a behaviour's props to the caller's handlers, `ref`, `className` and `style` is the React binding's job and doing it here would copy dependency source. Three behaviours are supplied outright (`useDismissableLayer` on `bindLayer` and `keepFocus`, `useRovingFocus` on `createRovingFocus`, `useTypeahead` on `createTypeahead`); the fourth is the gap entry above.

### The token rule

One file declares every colour, radius, shadow and spacing value: `apps/dashboard/src/styles/globals.css`. Maia's Zinc semantic pairs are declared in OKLCH in **both** `:root` and `.dark` and bridged to utilities by `@theme inline`, so a utility resolves to a token and a component states no value of its own.

- Page and surface read `--background`, `--card` and `--popover` with their `-foreground` partners; actions and focus read `--primary`, `--ring` and `--accent`; quiet surfaces and table headers read `--secondary`, `--muted` and `--accent`; destructive actions read `--destructive`; boundaries and inputs read `--border` and `--input`; data series read `--chart-1` to `--chart-5`.
- Additional semantic tokens exist only where the palette lacks the meaning: `--positive`, `--warning`, `--highlight` and `--overlay`, each with a foreground partner, each declared in both theme blocks and nowhere else.
- A status is never carried by colour alone. Every badge, gap, unknown, unavailable and simulated label carries a text label, so the four non-numeric states stay distinguishable without colour.
- Direction is a property of the content: `dir` goes on the block or document, spacing uses logical utilities, and no component carries a CSS base direction.
- Radius derives from Maia's `--radius` scale, spacing from Tailwind's scale plus `--spacing-target` for the 24 px minimum target, and motion from `tw-animate-css` under `prefers-reduced-motion`.

### The pipelines these fixtures exercise

**Images.** `prepareDisplayImage` in `src/modules/media/image.ts` settles the 10 MiB ceiling before a decoder sees the bytes, types the content by magic bytes so an extension cannot establish it, reads the header with `sharp.metadata()`, admits only JPEG, PNG and still WebP within 8,000 px per side, then applies `autoOrient()`, resizes to the 2,000 px longest edge with `fit: "inside"` and `withoutEnlargement: true`, re-encodes to the same format, and verifies the result: format still admitted, no residual metadata, no side over the cap, and no occurrence of the source file name in the delivered bytes. A failure yields a refusal with a reason and an action, never a kept asset.

**Video.** `src/modules/media/video.ts` inspects the upload with `mediabunny` — container, video and audio codecs, duration, dimensions and rotation — against the admitted profile (MP4 with H.264/AAC, or WebM with VP8/VP9 plus Vorbis/Opus; at most 100 MiB, 180 s and 1920 × 1080 after rotation), then copies the stream into a playback rendition without re-encoding, giving the conversion an empty tag set with `creationTime: null`. The served rendition is then re-inspected, and an asset is **rejected** if the container changed, a track count or codec changed, or any descriptive tag survived; `inspectVideo` reports that as `tags-residual` and no asset record is created.

**A disclosed limitation.** A copy-remux may retain an MP4 container's creation and modification timestamps. Descriptive tags are enforced by rejection, so no identifying metadata reaches a reader, but the residual timestamp behaviour is disclosed rather than hidden, and playback still depends on nothing beyond the browser's own decoder. The README carries the same limitation in its user-facing list.


`scripts/measure-workload.ts` prints the load average the run starts at, runs `apps/dashboard/e2e/workload-timing.spec.ts` with `WORKLOAD_MEASUREMENT=1` on that port — Playwright reuses the server already listening unless `CI` is set — prints the load average it ends at, and exits with the status the measurement's own assertions produced, so a missed budget fails the command instead of being printed and forgotten. The spec regenerates the workload itself through `bun run seed:workload`, because the runner's per-spec reset restores the seed and discards the workload document with it.

**The filtered Gifts page.** Everything is measured in Chromium against the running application, as the established worker, at `/support/gifts?from=2025-11-01&to=2026-10-31&currency=USD&page=0&pageSize=50` — the ledger query the plan names, resolved by the page's own Server Component through `reads.support.readGifts`. After three discarded warm-up loads there is **one run of exactly 30 page loads**, and the number reported is that run's p95: the samples sorted ascending and read at `ceil(0.95 × 30) − 1`, which is index 28 of 30. There is no attempt loop, no retry and no choice among runs, so a run that misses the 500 ms target is published as a miss.

**What one sample is.** The server read plus the first meaningful render. An init script installed before the navigation records, in the page's own clock, the first moment the ledger's whole-result summary exists in the document (`[data-slot="whole-result-summary"]`, checked once when parsing finishes and observed from before the document has a body), so the sample runs from the navigation's time origin and ends where the page first holds its figures — the server read, the response, the parse and the render together. Each sample is logged with the document request's own share of it (`responseStart − requestStart` from that navigation's Timing entry), so how much of a sample was the server's work is stated rather than inferred. Nothing is added to the application to produce it.

**The whole-query export.** The same run opens `/support/reports/received?from=2022-11-20&to=2026-11-21` — no currency filter and no page window, so the whole generated query is written — clicks that report's own "Export the whole query as CSV" control once, and times the click to the completed download. The file is parsed with the `csv-parse` the application fixes: its `#meta` `row_total` must equal the number of data records it carries, and both must exceed 90,000. That elapsed time and that row count are logged, and the elapsed time is asserted under 30 s.

**Why it is not part of `bun run test`.** Thirty page loads over the 67 MB workload document and one whole-query export take minutes, and the figures are an observation of this host rather than a gate over every change, so the cases run only when `WORKLOAD_MEASUREMENT=1` is set — which `bun run measure:workload` does — and the ordinary gate reports both as skipped, carrying that reason as the skip annotation, rather than timing anything.

**What the row count means.** The export writes `rowCount` 99,911 against a 100,000-row document because the grain is one authorised allocation: a gift with no allocation counts once, and a split gift contributes only the allocation this ministry may see. `rowCount` equals the whole-result count the same query's `readReport` states, which the published-workload measurement asserts; the print view builds its model from that same result, so its row total is that count too, and the exported file, the screen and the printed page agree on the same grain.

**Why the read costs what it costs.** The read is a whole-dataset operation: it reads the session's documents, validates the document set, projects 100,000 gift rows into report rows and aggregates the report. Three caches remove the parts that need not happen twice, and each is invalidated by the bytes rather than by a caller. `src/modules/store/repository.ts` keeps the parsed document set in a bounded least-recently-used memo — a byte budget across all sessions and an idle window, least recently read dropped first — and drops an entry whenever the modification time or size of any of the session's four files changes or this process writes or re-seeds. `src/modules/data-service/reads/support.ts` holds the validated workload document against the document object the store hands back, so 100,000 rows are validated once per document version rather than once per read, and holds that document version's latest support projection against the same object, rebuilt rather than accumulated when the support record's revision or the read's as-of instant moves — so a goal save, which bumps the revision, and a development clock change, which moves the as-of instant, each replace the projection the previous read left behind. Before those caches were added, the same reads measured by the earlier in-process harness were recorded at a p95 of 1,726.7 ms with repeats of 2,052.9 ms, 2,862.9 ms and 4,391.7 ms, and the export at 9,756.4 ms to 12,446.6 ms, because every read re-parsed the 67 MB document and re-validated all 100,000 rows.

**The table virtualiser is not installed.** `@tanstack/react-virtual` stays out. Every paged surface serves 50 rows by default, capped at 200, over pages the service processes — the partner-by-month matrix included, which serves 50 matrix rows per page beside the whole-result row total it states; the coaching surfaces state their own smaller window of 25 rows capped at 100. What decides it is a recorded rendered-row measurement, taken on the published workload above (10,000 partners, 100,000 gifts) against the dev server at `/support/reports/matrix?period=this-year` — the surface that renders the most rows of any one page, because it draws one table per currency partition — in headless Chrome at a 1280 × 900 viewport and again at 320 × 640, by reading the DOM node counts off the rendered page. The whole result is **8,932 partner rows** over 12 months and 5 currencies (EUR, JPY, KWD, UNKNOWN, USD), and the pager states "Showing 1–50 of 8,932 rows". At 1280 × 900 the page holds 5 currency partitions rendered as 5 tables — one presentation per partition, with no period-first list in the DOM — holding **250 `<tr>` body rows** (5 × 50) and **3,315 table cells**, and page 2 renders the same counts with a different first partner row. At 320 × 640 the same address holds 5 period-first sections, no table, **113 list items**, and no horizontal page scroll (`scrollWidth` 320 = `clientWidth` 320). One served page's payload is **50 rows of 8,932** (179 pages), 60 cells per row and **448,959 bytes**, with no copy of the query per cell; a stated size of 1,000 is served as **200 rows**, **1,745,829 bytes**. The largest window any surface renders is that matrix page, so the decision stands: the virtualiser is added only after a documented rendered-row measurement shows a window that needs one, recorded here in the same shape as the timings above.
